## What this branch changes (context for QA)

1. **The reported bug:** a doctor could see other doctors' earnings on the Finance Dashboard — worst for a user who holds both `Doctor` and `Clinic Admin` on the same clinic and chose "Enter as Doctor."
2. **Root cause fixed in two places:** the Finance Reports API had no role check beyond "logged in" (anyone could ask for any doctor's numbers), and the Finance Dashboard page decided "doctor view" from the user's raw roles instead of which panel they chose to view as.
3. **Doctor view is now narrower:** a doctor (not acting as admin) sees only their own OPD collection — no clinic-wide income, expenses, counter-session cash log, or handovers.
4. **Per-doctor fee configuration now actually works:** the "Fee Configs" screen used to have no effect on what patients were charged; it now does, when reception doesn't type an explicit override.
5. **New "Collection by Staff" section** on the (admin) Finance Dashboard — previously-built reporting that was never wired into any screen.
6. **New "Discounts" section** on the (admin) Finance Dashboard — every discount now records who gave it (doctor or reception), shown with name + role. Doctors keep the ability to give a discount themselves; this section is admin/reception-visible only, and is deliberately **not** part of the Amount Handovers screen/report.

Without this, applying any discount will fail at runtime (missing columns), not just show a wrong result.

## Round 3 fixes — DEF-FB-03 and DEF-FB-05 (10-Nov-2026)

Both were left as "by design" after round 2. To close the feature, both are now code-fixed on the same branch (`fix/finance-billing-access-control`), uncommitted.

### DEF-FB-03 — Doctor + Admin in "Doctor Panel" still got clinic-wide data from the API

**Why this needed more than "by design":** the role check was correct (this user genuinely has Clinic Admin rights), but the UI's "Doctor Panel" choice and the API's authorization decision were two independent signals that could disagree — exactly the shape of bug the original report was about, just reached by calling the API directly instead of clicking through the UI. Closing it meant making the panel choice something the API can actually see, without an Auth-repo change (out of scope per the cross-repo rule) — and without affecting the one case this endpoint must still work for: a plain Doctor viewing their own collection.

**Fix:** the same way the web client already tells the API which clinic is selected (`X-Application-Id` header, injected by `ClinicAuthorizationHandler`), it now also tells the API which panel the user chose, via a new `X-View-Scope: Doctor` header — sent only when `ClinicContextService.ActivePanel == "Doctor"` (i.e. only for the "🩺 Doctor Panel" entry point; never for "⚙️ Clinic Admin" or a plain doctor's default landing).

- `src/TenantCore.Web.Client/Services/ClinicAuthorizationHandler.cs` — injects `X-View-Scope: Doctor` when `ActivePanel == "Doctor"`.
- `src/TenantCore.Api/Controllers/ClinicControllerBase.cs` — new `IsDoctorPanelView()` helper reading that header.
- `src/TenantCore.Api/Controllers/FinanceReportsController.cs` — `GetDashboard`, `GetDaily`, `GetWeekly`, `GetMonthly`, `GetDateRange`, `GetReceptionWise`, `GetExpenseSummary`, `GetDiscounts` now return **403** when `IsDoctorPanelView()` is true, regardless of the caller's role — matching what a plain doctor already gets from these. `GetDoctorWise` is **not** forbidden (a doctor-panel view still needs "My OPD Collection"), but now self-scopes to the caller even if their role would otherwise let them request someone else's `doctorUserId`.
- `src/TenantCore.Api/Controllers/CounterSessionsController.cs` — `GetAll` (the clinic-wide cash-session list) gets the same 403 guard.
- New tests: `tests/TenantCore.Api.Tests/Controllers/FinanceReportsControllerTests.cs`, `tests/TenantCore.Api.Tests/Controllers/CounterSessionsControllerTests.cs` (8 tests, including the exact DEF-FB-03 scenario: a Doctor + Clinic Admin user with the header set gets 403/self-scoped, and a plain Doctor with the same header still gets their own data).

**Re-test (TC-FB-03, repeat with the API calls from DEF-FB-03's original steps):** log in as the Doctor + Admin user → clinic picker → "🩺 Doctor Panel" → call `dashboard`, `daily`, `weekly`, `monthly`, `date-range`, `reception-wise`, `expenses`, `discounts`, and `GET /api/counter-sessions` — all should now return **403**. Call `doctor-wise` (no `doctorUserId`) — should return only this user's own data. Call `doctor-wise?doctorUserId=<another doctor>` — should still return only this user's own data (the requested id is now ignored while in Doctor Panel). Then switch to "⚙️ Clinic Admin" and repeat — all should return 200 with full clinic data, unchanged from before.

### DEF-FB-05 — Registration form locks the fee when the doctor has a fee config

**Why this needed more than "by design":** the lock itself is a reasonable default (don't make reception retype a fee that's already configured), but TC-FB-32 showed there was no way to deliberately depart from it without clearing the doctor selection first — and the API has always accepted an explicit override. The fix keeps the helpful default but gives reception an explicit, visible way to use the override path the API already supports.

**Fix:** added an **"Override"** link next to the 🔒 lock note. Clicking it unlocks the Fee field in place (doctor selection stays, fee value stays until reception types a new one) — it does not silently change the fee, reception still has to type the number they want.

- `src/TenantCore.Web.Client/Pages/Opd/OpdRegistrationList.razor` — new `OverrideLockedFee()` method and "Override" button next to the lock message.

**Re-test (TC-FB-32):** Admin sets Doctor One's fee config to ₹777 → Receptionist → New OPD Entry → pick Doctor One (fee shows locked at 777.00) → click **Override** → field becomes editable → type ₹500 → submit. The visit should be created with fee **₹500**.
